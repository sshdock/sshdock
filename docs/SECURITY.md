# Security boundary and maintenance

SSHDock is a single-owner, single-node runtime for trusted Compose applications. A deploy key can operate all apps. Compose can mount host paths, use privileged containers or the Docker socket; Docker-group access is effectively host administration. Warnings about these settings are diagnostic, not a sandbox. Do not give deploy access to untrusted tenants.

The [Apache-2.0 OSS runtime](../LICENSE) and its manual deployment, diagnosis, recovery, and host-state backup/restore commands require no SSHDock account or hosted service. The VPS owner remains responsible for host security, application availability, application-data consistency, backup storage, and initiating and verifying recovery. No hosted operator or automatic recovery service is included.

Production remote access uses the installed OpenSSH forced Git and operator commands. The systemd daemon processes deployments; it does not expose a deployment HTTP API or require a separate SSH port. Keep the operating system, OpenSSH, Docker and Caddy patched and restrict the host's administrative SSH keys. The current unreleased source removes the embedded development SSH server; published v1.1.1 binaries still include it, outside the bootstrap-installed access path.

Application config is encrypted on disk. First-time key creation atomically publishes a complete private key without replacing a concurrent writer's key; existing invalid keys fail explicitly instead of being regenerated. Its local key, database and backup archives must be protected together. Config reveal and container exec intentionally expose requested data to the trusted operator. Redaction covers known stored config values in ordinary output, not arbitrary transformed values, secrets embedded in application images, or secrets deliberately revealed by an owner. Registry credentials belong to the Docker user/credential helper; they are not application config. See [external-build credentials](EXTERNAL_BUILDS.md#credentials-and-artifact-retention).

Build SSHDock with Go **1.26.10 or newer**. The minimum patch toolchain addresses the standard-library advisories identified by the v1 audit and subsequent security scans. That audit also updated the SSH dependency used by the now-removed development listener. CI runs `make ci` and `make security`; release packaging requires the same workflow to pass first. `make security` runs pinned `govulncheck` against the current official Go vulnerability database and fails on reachable vulnerable symbols. Run it again before releasing: a passing scan is evidence at that time, not a permanent absence-of-vulnerabilities claim.

Host-state extraction confines filesystem operations to its temporary directory using Go's `os.Root`, including nested symlink resolution. Restore requires a trusted archive and stopped runtime; it replaces configured SSHDock state and does not restore Docker volume contents. Separate manual volume restore validates the complete archive and extracts its supported ordinary files/directories only into a newly created volume; existing targets are refused. It is host administration, without a restricted-SSH privilege expansion.

Host-state archives are unencrypted and include the config decryption key. Volume archives and database dumps are also unencrypted and may contain secrets. Treat them as credentials: restrict permissions and use your own encryption and protected storage before transferring them. Volume inventory and retained live data do not prove archive recovery. The [manual data guide](APPLICATION_DATA_BACKUPS.md) explains stopped-writer responsibility, limited filesystem metadata, PostgreSQL-native consistency and fresh-target restore. Docker access remains a trusted-owner capability, not workload isolation.

The upstream [Go release history](https://go.dev/doc/devel/release) documents supported toolchain fixes. The [Go vulnerability database](https://pkg.go.dev/vuln/) provides the source advisories; scanners may report library call paths whose actual exposure depends on the configured access path. Application images and host packages need their own patching and scans.

Keep private deployment evidence, keys, production domains, backup paths and raw logs out of public issues. Report reproducible non-sensitive reliability problems in the issue tracker; arrange a private channel with a maintainer before sharing a security report containing exploit details or credentials.
