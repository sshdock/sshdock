# v1.1 candidate validation

This report records the verified scope for [issue #59](https://github.com/sshdock/sshdock/issues/59). It does not announce a v1.1 release or an anonymous-installation PASS. The historical [v1.0.0 validation](RELEASE_ACCEPTANCE.md) remains a separate report.

## Source and environment

The current runtime candidate is [09a8edd](https://github.com/sshdock/sshdock/commit/09a8edde0ffc8ebdd74789064cf333c11ba22287). Its Linux amd64 CLI, daemon and compiled integration-test binary were built from the exact Git archive with full-source-version linker flags; archive provenance, binary architecture, installed versions and artifact integrity were verified.

The initial cleared-runtime source installation used [4aeaffb](https://github.com/sshdock/sshdock/commit/4aeaffbed2246603fa62bfd734efa75dd6c49197). The populated v1.0.0 upgrade, repeat install and corrected Caddy retry guidance were exercised on 09a8edd. The distinction is retained rather than claiming a fresh installation of every intermediate candidate.

Live checks used one dedicated Ubuntu 24.04 amd64 VPS after authorized software/data resets. Existing OS, OpenSSH/admin access, Docker/Compose/Caddy and external DNS/firewall prerequisites were retained. No OS reimage, second-VPS restoration or local Docker execution is claimed.

The complete v1.0.0 framework/software/example, browser and long-observation matrix was **not rerun** for this candidate. This report covers focused v1.1 journeys and the explicitly reused unchanged backup paths below. The historical report is evidence of that earlier revision, not a current-candidate full-matrix PASS; the broader release guidance in [TESTING.md](TESTING.md) must not be read as completed by these focused checks.

## Retained friction and interpretation

First public HTTPS was observed after 323.55 seconds, including an incorrectly supplied Caddy admin URL, 299 failed TCP checks and manual correction to the required bare `host:port` form. The post-correction observation was 13.93 seconds. These are observations of this run, not clean-install timing or a performance promise. Separate first-HTTPS checks for new hostnames retained 16 TLS alerts and three TCP failures; no later sampled failure followed a success for the same hostname. Their timing alone does not prove a certificate-issuance cause or continuous availability.

The first failure also exposed misleading retry guidance: redeploy skips initial auto-routing when a domain already exists. The corrected candidate names the concrete route reattachment command and that command was exercised live.

The native agent followed [skill installation](AGENT_OPERATIONS.md), [structured inspection](JSON_OUTPUT.md), [server preflight](PREFLIGHT.md) and [manual Git recovery](RECOVERY.md). Its disposable Compose app used a health check, restart policy and loopback-published HTTP service. After normal A deployment, B selected a nonexistent image; the agent inspected that exact failed attempt and separately identified A as the last success. An explicitly approved force-with-lease using B's full expected SHA selected locally verified A. Recovery was verified using its new deployment ID, not A's historical success. No SSHDock-specific agent API or administrator Docker access was used.

Two private launcher errors occurred before the model started and were corrected. During the actual session, normal workstation sandbox review allowed required Git metadata writes; push-side local tracking-ref warnings did not prevent server acceptance. Exact server queries established the outcomes. Full private session events were retained, including streamed effective Compose output; the stateless fixture had no configured secrets. Local Docker/preflight was skipped under the owner's constraint, while documented server preflight ran.

Successful deployment/query status does not prove route application, DNS/TLS, application data correctness or uninterrupted public availability. Nonzero bounded ingress observations remain retained; eventual recovery does not erase them. Preflight reports only observed facts and does not pull/build images or prove application readiness.

Application archives are unencrypted and can contain secrets; host-state archives include the config decryption key. Reused archive recovery proves the documented manual scope after source data removal, not a universal live snapshot or two-VPS migration. Git recovery does not undo database migrations or external changes. The platform remains trusted-operator, single-node Compose, without automatic rollback, workload isolation, zero-downtime cutover or an availability SLA.
